## Stage

Implementation started (2026-08-29). Domain model and architecture are settled (see `03_DOMAIN_MODEL.md`'s Decisions and ADRs); the Core is now being built out incrementally. `src/core/domain/` has the `KnowledgeElement` base abstraction (CORE-001) and `Node` (CORE-002), both merged to `dev` with unit tests. `src/adapters/foundry/` has the first Foundry Adapter slice (ADAPT-001, merged to `dev`): `mapJournalEntryPageToNode`, a pure JournalEntryPage-to-Node mapping. A real, installable Foundry module scaffold now exists too (ADAPT-002, per ADR-0006): `module.json`, `src/adapters/foundry/module-entry.ts`, and a dedicated `build:foundry-module` build target — built, released and manually installed by the user; confirmed loading in a live Foundry v14 GM session at `localhost:30000` (building itself is still a manual, locally-run step, since neither of this session's environments can run `vite build` — see ADR-0006's Context). `package.json`/`tsconfig.json`/`vitest.config.ts`/`eslint.config.js` scaffold the TypeScript/Vite/Vitest/ESLint/Prettier stack from `README.md`. Real Foundry data is now flowing through both Adapter slices: all 41 real Actors and all 61 real Journal Pages from the "Academia El Último Norte" campaign map cleanly to Nodes (verified 2026-08-30 — see `SESSION_LOG.md`). What's still missing is a place to persist that output and a View to look at it through. Storage is now decided (STORE-001, issue #32, `decisions/ADR-0008-storage-provider.md`, 2026-08-31): embedded SQLite as the primary store, with a deliberate user-triggered export (a generated JSON snapshot) as the reachability path for a future standalone frontend — read-only for now, motivated by wanting to hand the campaign's knowledge graph to an external AI agent for planning. `01_ARCHITECTURE.md`'s Application layer already has room for that standalone client ("Web UI" alongside Foundry), so it doesn't change the Core. That Worker/OPFS feasibility spike is now resolved (STORE-002, 2026-08-31, see ADR-0008's addendum). `Relationship` (Core domain, CORE-003, 2026-08-31) is also now implemented and merged, instance-only (see `03_DOMAIN_MODEL.md`'s Decisions). ADAPT-003 (Foundry UI extension/customization, issue #20) is now done and merged to `dev`, as an opt-in header-control button rather than the originally-shipped permanent bar — see item 8 below and `decisions/ADR-0009-foundry-ui-extension-hooks.md`'s Amendment. The real Storage Provider is now implemented and live-verified (STORE-003, issue #38, 2026-09-06): `src/core/storage/storage-provider.ts` defines the engine-agnostic `StorageProvider` port Core/Adapters program against; `src/storage/sqlite/` implements it with the official `@sqlite.org/sqlite-wasm` package (`opfs-sahpool` VFS, real SQL schema/migrations via `PRAGMA user_version`, real indexes for ADR-0007's 1-hop lookup, deliberately no FK on `Relationship.origin`/`target` per ADR-0007/ADR-0008); `src/core/storage/to-portable-snapshot.ts` is the Core-owned, full/unredacted JSON export ADR-0008 settled on. The Foundry Adapter's existing mappings (`mapActorToNode`, `mapJournalEntryPageToNode`) now actually persist via `src/adapters/foundry/storage-sync.ts`, wired into real Foundry Hooks (`createActor`/`updateActor`/`createJournalEntryPage`/`updateJournalEntryPage`, plus a `ready`-time backfill) in `module-entry.ts` — confirmed live in a real Foundry reload: a 94KB SQLite file persisting to OPFS with clean console logs. `RelationshipDefinition` is now real Core state too (CORE-004, issue #39, 2026-09-06): `src/core/domain/relationship-definition.ts` implements `inverse`/`cardinality`/`symmetry`/`traversalCategory`/an optional `validation` Node-type allow-list, per ADR-0007 — deliberately Core-domain-only (no storage persistence yet); `Relationship.definitionId` stays an unchanged plain string reference. Current focus: with STORE-003 and CORE-004 both merged, product-owner scoped the path to Alberto's stated goal ("a visual interface for me to start defining relations in Foundry so when we select something — city, actor, scene — we can bring the graph to life") into three new tickets: **CORE-005** (issue #42, implement-only — the Core Query API executing ADR-0007's 3 traversal presets, fully unblocked now that STORE-003/CORE-004 exist), **ADAPT-006** (issue #43, decide-only — how a GM actually authors a Relationship instance between two Nodes in Foundry; explicitly not assumed to reuse ADAPT-003's single-document tagging pattern, since picking two arbitrary entities is a materially different shape), and **VIEW-001** (issue #44, decide-only — the graph View's rendering/interaction design, including ADR-0007's own named open item on content-prominence ordering). Sequencing: ADAPT-006 is the very next action (ux-ui-designer) since it directly blocks Alberto's literal ask and has zero design decided yet; CORE-005 (software-developer) has no dependency on ADAPT-006's outcome and can slot in alongside it; VIEW-001's design pass can start in parallel but its implementation is last, needing both CORE-005 and real authored Relationship data to be meaningful. Other open backlog candidates, lower priority: persisting `RelationshipDefinition` now that the Storage Provider exists (fast-follow, deliberately left out of CORE-004), the Scene→Block mapping (ADAPT-005 decided, not implemented), Node deletion policy (still explicitly open per ADR-0007), JournalEntry/Scene tagging UI (the same ADAPT-003 mechanism applied elsewhere), and a real export-trigger UI (today it's a console-only `game.modules.get('archivexus').api.exportSnapshot()` call).

## Target users

Tabletop RPG Game Masters running campaigns in Foundry VTT who want a connected memory of their world (characters, locations, organizations, events, relationships, history) instead of fragmented, hard-to-navigate documents.

## Tech stack

Planned, per `README.md`: TypeScript (core language), Foundry VTT API (primary platform integration), Vite (dev tooling), Vitest (unit testing), ESLint, Prettier. Architecture is intentionally platform-agnostic at the Core (see `01_ARCHITECTURE.md`); Foundry is the first Adapter, not a Core dependency.

## Constraints

Installing, updating, enabling or disabling a module inside a live Foundry world is always a manual action performed by the user (GM) — never by an agent or this session's automation (ADR-0006). Otherwise none formally documented yet; worth capturing here once more appear (time budget, whether this ships as a paid Foundry module, compatibility requirements with specific Foundry versions, etc.).
