# Project

> The operational snapshot of this project. This is the file agents read first, and the one to update most often — whenever the stage, priorities, or constraints actually change.

## Name

Archivexus

## Type

- [x] Personal / fun project

Confirmed 2026-08-26: built for personal use in tabletop campaigns, no commercial goal for now. Agents should favor speed and simplicity over process here.

## Stage

Implementation started (2026-08-29). Domain model and architecture are settled (see `03_DOMAIN_MODEL.md`'s Decisions and ADRs); the Core is now being built out incrementally. `src/core/domain/` has the `KnowledgeElement` base abstraction (CORE-001) and `Node` (CORE-002), both merged to `dev` with unit tests. `src/adapters/foundry/` has the first Foundry Adapter slice (ADAPT-001, merged to `dev`): `mapJournalEntryPageToNode`, a pure JournalEntryPage-to-Node mapping. A real, installable Foundry module scaffold now exists too (ADAPT-002, per ADR-0006): `module.json`, `src/adapters/foundry/module-entry.ts`, and a dedicated `build:foundry-module` build target — built, released and manually installed by the user; confirmed loading in a live Foundry v14 GM session at `localhost:30000` (building itself is still a manual, locally-run step, since neither of this session's environments can run `vite build` — see ADR-0006's Context). `package.json`/`tsconfig.json`/`vitest.config.ts`/`eslint.config.js` scaffold the TypeScript/Vite/Vitest/ESLint/Prettier stack from `README.md`. Real Foundry data is now flowing through both Adapter slices: all 41 real Actors and all 61 real Journal Pages from the "Academia El Último Norte" campaign map cleanly to Nodes (verified 2026-08-30 — see `SESSION_LOG.md`). What's still missing is a place to persist that output and a View to look at it through. Storage is now decided (STORE-001, issue #32, `decisions/ADR-0008-storage-provider.md`, 2026-08-31): embedded SQLite as the primary store, with a deliberate user-triggered export (a generated JSON snapshot) as the reachability path for a future standalone frontend — read-only for now, motivated by wanting to hand the campaign's knowledge graph to an external AI agent for planning. `01_ARCHITECTURE.md`'s Application layer already has room for that standalone client ("Web UI" alongside Foundry), so it doesn't change the Core. That Worker/OPFS feasibility spike is now resolved (STORE-002, 2026-08-31, see ADR-0008's addendum) — implementing the Storage Provider itself is separate follow-up work, not yet started. `Relationship` (Core domain, CORE-003, 2026-08-31) is also now implemented and merged, instance-only (see `03_DOMAIN_MODEL.md`'s Decisions). ADAPT-003 (Foundry UI extension/customization, issue #20) is now done too, as an opt-in header-control button rather than the originally-shipped permanent bar — see item 8 below and `decisions/ADR-0009-foundry-ui-extension-hooks.md`'s Amendment. Current focus: not yet chosen for the next session.

## Target users

Tabletop RPG Game Masters running campaigns in Foundry VTT who want a connected memory of their world (characters, locations, organizations, events, relationships, history) instead of fragmented, hard-to-navigate documents.

## Tech stack

Planned, per `README.md`: TypeScript (core language), Foundry VTT API (primary platform integration), Vite (dev tooling), Vitest (unit testing), ESLint, Prettier. Architecture is intentionally platform-agnostic at the Core (see `01_ARCHITECTURE.md`); Foundry is the first Adapter, not a Core dependency.

## Constraints

Installing, updating, enabling or disabling a module inside a live Foundry world is always a manual action performed by the user (GM) — never by an agent or this session's automation (ADR-0006). Otherwise none formally documented yet; worth capturing here once more appear (time budget, whether this ships as a paid Foundry module, compatibility requirements with specific Foundry versions, etc.).

5. ~~Foundry Adapter — map `Actor` to Node~~ — done, `src/adapters/foundry/actor-to-node.ts` (ADAPT-004, issue #22). `mapActorToNode`, same pattern as ADAPT-001: id from uuid, title from name, type from an explicit `flags.archivexus.nodeType` flag falling back to `Character`, visibility from `ownership.default`. Deliberately does not branch on Foundry's own `actor.type` (character/npc/encounter/group, confirmed from the real "Academia El Último Norte" campaign's 41 Actors) — product-owner call on issue #22, consistent with ADAPT-001's no-content-inference rule. Validated against 4 real Actors, one per real `actor.type`.
6. ~~Fix Node title collisions on generic Foundry page names~~ — done (#25). Real campaign data showed 5 distinct NPCs' "Retrato" (Portrait) pages collapsing to the same Node title. `mapJournalEntryPageToNode` now qualifies the title with the parent JournalEntry's name when it disambiguates anything (`FoundryJournalEntryPageLike.parent.name`), falling back to the bare page name otherwise — fully backward compatible.
7. ~~Decide how Foundry `Scene`s map into Archivexus~~ — decided (ADAPT-005, issue #23, 2026-08-31): a Scene is never its own Node (same reasoning as `JournalEntry`) — it's a `scene`-type Block on whatever Node the GM explicitly links it to, and stays unmapped (not force-created as a placeholder Node) if the GM hasn't linked it yet. This also settled Block's real shape for the first time (`{ type, uuid, title? }`, always a Foundry-element reference — see `03_DOMAIN_MODEL.md`'s Knowledge Element Decisions), replacing `Block.data: unknown`'s placeholder. Implementing the mapping itself (`mapSceneToBlock` or similar, plus updating `Block`'s real TS type in `src/core/domain/block.ts`) is separate, not-yet-scoped follow-up work — this ticket was decide-only.
8. ~~Foundry UI extension/customization~~ (ADAPT-003, issue #20) — done, live-verified (`src/adapters/foundry/actor-node-type-tag.ts`, 2026-08-31, `decisions/ADR-0009-foundry-ui-extension-hooks.md`). Went through two implementations: first, a permanent tagging bar injected into every Actor sheet via `renderActorSheetV2` — built, found and fixed a real DOM-overlap bug via live testing (the control overlapped Foundry's floating title bar; fixed by inserting after `.window-header` instead of inside `.window-content`, ADR-0009's Correction), then fully verified end-to-end (a typed value saves to `actor.flags.archivexus.nodeType` via Foundry's native form handling). Alberto then challenged it on two fronts — its position, and a more fundamental "is this even necessary?" — and a grep confirmed nothing in Core reads `Node.type` yet, so the permanent bar had zero current visible payoff for the common case (a Player Character already gets the right type for free from `ACTOR_FALLBACK_NODE_TYPE`). Redesigned per Alberto's choice into an **opt-in header-control button**: `getHeaderControlsActorSheetV2` pushes a button into the sheet's header-controls dropdown, which opens a `DialogV2.prompt` dialog (`buildNodeTypeDialogContent`, pure/unit-tested) only when a GM actively wants to reclassify something — no more persistent DOM injection at all. See ADR-0009's Amendment for the full reasoning and live-verification notes (including the "header controls aren't recomputed by a plain re-render, only a close+reopen" gotcha). Scoped to Actor first, matching every prior Adapter ticket's incremental-per-document-type shape; JournalEntry/Scene tagging UI is separate, not-yet-scoped follow-up work.
9. ~~Relationship~~ (Core domain, per ADR-0005) — done, merged to `dev` (CORE-003, 2026-08-31): `src/core/domain/relationship.ts` implements the Relationship instance shape (`origin`/`target` Node ids, `definitionId`, composed from KnowledgeElement exactly like Node), mirroring CORE-002's pattern, with unit tests (`relationship.test.ts`, including rejecting self-relationships — `03_DOMAIN_MODEL.md`'s "Can a Relationship connect a Node to itself?" Decision, added during reviewer pass) and exported from `src/core/domain/index.ts`. Deliberately scoped to the instance only — Relationship Definition itself (inverse/cardinality/symmetry/validation/traversalCategory as real, versioned Core state per ADR-0007) is separate, not-yet-scoped follow-up work; `definitionId` is just a string reference for now. Then View, lower priority still since it depends on having enough Nodes/Relationships worth projecting; its own MVP scope (3 fixed traversal presets, no open config) is settled by ADR-0007.
10. ~~Decide Archivexus's Storage Provider~~ — done (STORE-001, issue #32, 2026-08-31): `decisions/ADR-0008-storage-provider.md` settled on embedded SQLite (WASM, `opfs-sahpool` VFS) as the primary store, satisfying ADR-0007's 1-hop-lookup and no-cascading-FK constraints via real indexes, plus a deliberate user-triggered export (a generated JSON snapshot, not a raw copy of the SQLite file) as the reachability mechanism for a future standalone frontend/external AI agent — no live sync, read-only for now. `01_ARCHITECTURE.md`'s Storage section updated to match. The one implementation-risk item ADR-0008 carried forward — whether dedicated-Worker creation and `opfs-sahpool` behave cleanly inside a real running Foundry client — is now resolved: a STORE-002 spike confirmed it works (see ADR-0008's addendum), after finding and fixing a real Vite `base`-path bug along the way (`vite.foundry.config.ts` now uses a relative base). Implementing the Storage Provider itself and the export/View/UI that reads from it are still out of scope — separate follow-up work, now unblocked with no known feasibility risk remaining.
